# Notifications API

The Notifications API manages in-app notifications generated by system events and administrative transitions (such as task assignments, resolution updates, forwarding decisions, and cancellations). This subsystem informs actors of relevant changes regarding reports they own or are assigned to resolve.

---

## Endpoint Summary

The In-App Notifications controller registers exactly **4 operations** under `/api/v1/notifications`:

| Method | Endpoint | Roles | Scope | Purpose |
| :---: | :--- | :--- | :--- | :--- |
| **GET** | `/api/v1/notifications` | Any Authenticated User | Owner | Retrieve all notifications for the calling user, sorted by newest first. |
| **GET** | `/api/v1/notifications/unread-count` | Any Authenticated User | Owner | Retrieve the total count of unread notifications for the calling user. |
| **PATCH** | `/api/v1/notifications/{notification_id}/read` | Any Authenticated User | Owner | Mark a specific notification as read. |
| **PATCH** | `/api/v1/notifications/read-all` | Any Authenticated User | Owner | Mark all unread notifications for the calling user as read. |

---

## Notification Delivery Model

* **In-App Database Storage:** In-app notifications are stored persistently in the database (`in_app_notifications` table). These are fetched dynamically on demand.
* **No Real-Time Transport:** There is **no WebSocket, SSE (Server-Sent Events), or push notification transport** implemented in the current system. Clients must poll the listing or unread-count endpoints to fetch new notifications.
* **Email Integration:** Certain actions also trigger async emails (such as invitations, OTP verification, or resolution approvals) processed via SMTP templates. Refer to [In-App Notifications vs Email](#in-app-notifications-vs-email) below.

---

## Notification Data Model

The `InAppNotification` entity represents a system-generated alert:

| Field | Type | Nullable | Description |
| :--- | :--- | :---: | :--- |
| `id` | Integer | No | Database primary key of the notification record. |
| `user_id` | Integer | No | ID of the recipient user. |
| `report_id` | Integer | Yes | Mapped report ID (allows navigation/deep-linking from notification). |
| `title` | String(150) | No | Notification title header. |
| `message` | Text | No | Notification body text details. |
| `type` | String(50) | No | System category string (e.g. `NEW_ASSIGNMENT`, `WORK_STARTED`). |
| `is_read` | Boolean | No | Read status flag (defaults to `false`). |
| `created_at` | DateTime | No | Creation timestamp (server defaults to current time). |

## Notification Types

The following categories of notifications are generated by the backend service layer:

| Type / Trigger | Recipient | Created When | Related Resource |
| :--- | :--- | :--- | :--- |
| `NEW_ASSIGNMENT` | Worker | Worker is assigned a report (automatically or manually). | `report_id` |
| `WORK_STARTED` | Citizen | Worker clicks "Start Work" on an assignment. | `report_id` |
| `RESOLUTION_APPROVED` | Worker | Worker's resolution is approved (via AI check or manual review). | `report_id` |
| `REPORT_RESOLVED` | Citizen | Report resolution is approved, marking report as resolved. | `report_id` |
| `MANUAL_REVIEW` | Worker | Resolution submission fails AI checks and routes to manual review. | `report_id` |
| `RESOLUTION_REJECTED` | Worker | Department Admin rejects submitted resolution. | `report_id` |
| `ASSIGNMENT_CANCELLED` | Worker | Department Admin cancels assignment (due to cancellation/forwarding). | `report_id` |
| `REPORT_CANCELLED` | Citizen | Department Admin cancels a report. | `report_id` |
| `REPORT_REOPENED` | Citizen | Department Admin reopens a resolved report. | `report_id` |
| `FORWARD_SENT` | Source Admin | Forward request is sent to destination department. | `report_id` |
| `FORWARD_REQUEST` | Destination Admins | Incoming forward request is queued for destination review. | `report_id` |
| `FORWARD_APPROVED` | Worker | Worker's forward request is approved by source admin. | `report_id` |
| `FORWARD_ACCEPTED` | Citizen / Source Admins | Destination Admin accepts forwarded report. | `report_id` |
| `FORWARD_DECLINED` | Citizen / Source Admins | Destination Admin declines forwarded report (returns to source). | `report_id` |
| `REPORT_REASSIGNED` | Worker | Forward is declined, returning the assignment to original worker. | `report_id` |

## Notification Recipient Rules

* **Citizen Notifications:** Citizens are notified when repair work starts (`WORK_STARTED`), when their issue is resolved (`REPORT_RESOLVED`), when their report is cancelled (`REPORT_CANCELLED`) or reopened (`REPORT_REOPENED`), and when forward requests change states (`FORWARD_ACCEPTED`, `FORWARD_DECLINED`).
* **Worker Notifications:** Workers are notified when assigned a task (`NEW_ASSIGNMENT`), when their resolution is approved (`RESOLUTION_APPROVED`), rejected (`RESOLUTION_REJECTED`), or routed for manual check (`MANUAL_REVIEW`), when an assignment is cancelled (`ASSIGNMENT_CANCELLED`), when their forward request is approved (`FORWARD_APPROVED`), and when a declined forward task is reassigned back (`REPORT_REASSIGNED`).
* **Department Admin Notifications:** Department Admins are notified of incoming requests (`FORWARD_REQUEST`) routed to their department, and when outgoing forwards are accepted/declined (`FORWARD_ACCEPTED`, `FORWARD_DECLINED`) or successfully sent (`FORWARD_SENT`).
* **City Admin / Super Admin:** These roles do not receive transaction-level notifications since they oversee global analytics rather than localized queues.

---

## Read State Semantics

* **Initial State:** Notifications are logged with `is_read = False`.
* **State Transition:** Reading occurs via explicit PATCH requests:
  * Call `PATCH /api/v1/notifications/{notification_id}/read` to set `is_read = True` on a specific alert.
  * Call `PATCH /api/v1/notifications/read-all` to set `is_read = True` on all unread notifications for the user.
* **Metadata Limits:** The backend does **not** store a separate `read_at` timestamp.
* **Unread Filtering:** The `unread-count` query performs a direct database count of records where `is_read = False`.

---

## In-App Notifications vs Email

The system separates standard in-app notifications from administrative emails:

### 1. In-App Notifications (Persisted Database Alerts)
* Standard report lifecycle updates (assignment, work started, resolution approval, manual review, cancellations, forwarding).

### 2. Transactional Emails (SMTP Notifications)
* **Otp Delivery:** Login OTP and Password Reset OTP codes.
* **Invitations:** Registration invitations sent to new Workers, Department Admins, and City Admins containing activation links.
* **Account Status:** Notifications for account activation success, blocks, and unblocks.
* **Resolution Completed:** When a report is successfully resolved (approved manually or by AI), the system sends a confirmation email to the citizen alongside the in-app notification.

## Detailed Endpoint Specifications

---

## `GET /api/v1/notifications`

### Purpose
Retrieves all notifications for the calling user, sorted by newest first.

### Roles / Authorization
* Any authenticated user. Scoped strictly to the caller's `user_id`.

### Authentication
* Bearer Access Token required.

### Headers
* `Authorization: Bearer <access_token>`

### Success Response
* **HTTP Status:** `200 OK`
* **Response Model:** `list[NotificationResponse]`

| Field | Type | Nullable | Description |
| :--- | :--- | :---: | :--- |
| `id` | Integer | No | Primary key of notification. |
| `report_id` | Integer \| null | Yes | Mapped report ID for navigation. |
| `title` | String | No | Title text. |
| `message` | String | No | Message text. |
| `type` | String | No | System notification type category. |
| `is_read` | Boolean | No | Read status flag. |
| `created_at` | DateTime | No | Creation timestamp. |

### Example Success Response
```json
[
  {
    "id": 142,
    "report_id": 92,
    "title": "New Assignment",
    "message": "You have been assigned a new civic issue.",
    "type": "NEW_ASSIGNMENT",
    "is_read": false,
    "created_at": "2026-07-28T16:00:00Z"
  }
]
```

## `GET /api/v1/notifications/unread-count`

### Purpose
Retrieves the total count of unread notifications for the calling user.

### Roles / Authorization
* Any authenticated user. Scoped strictly to the caller's `user_id`.

### Success Response
* **HTTP Status:** `200 OK`
* **Response Model:** `UnreadNotificationResponse`

```json
{
  "unread_count": 3
}
```

---

## `PATCH /api/v1/notifications/{notification_id}/read`

### Purpose
Marks a specific notification as read.

### Roles / Authorization
* Any authenticated user. The caller must own the target notification.

### Path Parameters

| Name | Type | Required | Description |
| :--- | :--- | :---: | :--- |
| `notification_id` | Integer | Yes | Database ID of the notification. |

### Validation Rules
* **Ownership Verification:** The query filters by both `notification_id` and `user_id`. If the notification does not exist or belongs to another user, the API returns `404 Not Found` (rather than a 403) to prevent resource enumeration.

### Business Flow
1. Authenticates current user.
2. Queries the notification record matching `id` and `user_id`.
3. If not found, throws `404`.
4. Sets `is_read = True`.
5. Commits transaction and returns a confirmation.

### Success Response
* **HTTP Status:** `200 OK`

```json
{
  "success": true,
  "message": "Notification marked as read."
}
```

### Error Responses
| HTTP Status | Condition | Response / Detail |
| :---: | :--- | :--- |
| **401** | Missing/invalid token. | `{"detail": "Invalid or expired token."}` |
| **404** | Notification does not exist or belongs to another user. | `{"detail": "Notification not found."}` |

---

## `PATCH /api/v1/notifications/read-all`

### Purpose
Marks all unread notifications for the calling user as read.

### Roles / Authorization
* Any authenticated user.

### Success Response
* **HTTP Status:** `200 OK`

```json
{
  "success": true,
  "updated": 3
}
```

## Frontend Integration Notes

* **Unread Badge Support:** Fetch `GET /api/v1/notifications/unread-count` on app initialization and display the badge in the navigation header.
* **Deep Linking / Navigation:** When a user taps an in-app notification, read the `report_id` property. If present, the client should navigate directly to the detailed view page for that report.
* **No Real-Time Transport:** The API has no WebSocket, SSE, or push notification layer. Client applications that require live notification counts must poll `GET /api/v1/notifications/unread-count` or `GET /api/v1/notifications` on page transition or at a frequency appropriate to the application's needs. No specific polling interval is enforced by the API contract.
